## Goal

Convert the migration roadmap into concrete, trackable tasks with explicit quality, testing, UX consistency, and performance validation.

## Strategic hold — internal infrastructure first

> **Decision recorded 2026-03-09**: All feature-migration work (Phases 4–10, i.e. preview automation, fleet control, module parity) is on hold until the internal platform infrastructure is production-ready.

> **Hold lifted 2026-03-09**: All four Phase 12 completion criteria are now satisfied (T131 ✅ T108 ✅ T106 ✅ T107 ✅). Feature migration (Phase 4 and beyond) may now resume.

**Rationale**: modules to be migrated (deployment, orchestration, project, service, github) all depend on:
- Active-active load balancer routing being deterministic and fault-tolerant (Phase 12)
- Mesh topology and event replication being reliable under partition scenarios (Phase 11)
- Cluster signing key distribution and rotation being solid (Phase 12 — T123–T128, T158–T160)
- Trust model hardening (T108) so internal mesh calls cannot be spoofed or replayed

Migrating on top of unreliable infrastructure creates double work: bugs in routing or secret management will cascade into migrated feature modules and require re-work.

**Completion criteria for the hold to lift (minimum):**
- [x] T131 — Chaos and partition validation for active-active routing (all scenarios green)
- [x] T108 — Mesh trust/security model (signed control envelopes, replay-window guards)
- [x] T106 — Event stream replication over mesh (cursor-based replay)
- [x] T107 — Partition/failover policies (AP/CP modes, degraded-mode behavior)

All criteria met. Phase 4 (preview automation) can now begin in parallel with T109–T112.

## Architecture decomposition note (v1/v2 -> v3 improvement)

To reduce "god service" risk in `DeploymentService`, v3 now adopts explicit plugin boundaries while preserving v1/v2 adapter intent:

- **Provider boundary**: `SourceProviderRegistryService` routes to source providers that share one interface (currently `GithubSourceProviderService`, with room for GitLab/Git/Upload implementations).
- **Runner boundary**: `RuntimeRunnerRegistryService` routes runtime execution via one runner interface (currently `DockerRuntimeRunnerService`, with alias slots for `dockerfile`, `docker_compose`, `nixpacks`, etc.).
- **Orchestrator boundary**: `DeploymentService` remains the workflow coordinator (queue lifecycle, persistence, events) and no longer embeds provider-specific checkout validation or container/runtime implementation details.

This keeps orchestration logic focused on use-cases and allows future provider/runner additions without widening `DeploymentService`.
